# 代谢覆盖性能验证

## 实现与边界

目录构建现在复用本次请求已验证、已解析的数据库，直接调用原有官方完整性计算。原流程会在同一请求内再次读取数据库。进程内最多保留 8 份完整性报告，缓存键包含数据库路径、已验证清单哈希、完整基因面板和数据库版本。同一缓存键的并发计算只执行一次。

目录快照增加最多 8 份已序列化响应缓存。每次请求仍重新计算来源指纹、读取磁盘快照并检查文件哈希。命中时省去重复的 JSON 解析和编码；磁盘快照或任何来源变化时重新验证。全部后端源码参与指纹的原有规则保持不变。

实验来源继续单独读取实验记录，不使用当前模型目录快照。本次没有重新运行实验，也没有修改冻结结果。接口路径和 JSON 结构保持兼容。

## 测试

在项目根目录执行：

```powershell
.venv\Scripts\python.exe -m pytest backend/tests/test_coverage_performance.py backend/tests/test_coverage_catalog.py backend/tests/test_catalog_snapshot.py -q
```

最终结果：`19 passed, 6 warnings in 38.27s`。警告来自测试客户端和科学依赖。新增测试覆盖数据库只加载一次、并发缓存只构建一次、面板与清单变化失效、磁盘篡改失效、构建期间输入变化拒绝、后端源码变化失效，以及持久缓存命中时无需导入 scCellFie 或 AnnData。

修改的后端源码通过 Ruff 和 BasedPyright 检查，后者为 0 错误、0 警告。相关文件的 `git diff --check` 通过。

## 实际计时

以下为同一机器上独立 Python 进程的模型目录构建，未创建实验记录。

| 阶段 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 第一次数据库加载，包含科学依赖导入 | 28.5709 秒 | 24.6698 秒 |
| 同一请求中的重复数据库加载 | 0.1868 秒 | 已移除 |
| 官方完整性计算 | 13.6368 秒 | 13.7886 秒 |
| 目录关联补充 | 0.2345 秒 | 0.2764 秒 |
| 分类注释读取 | 0.4159 秒 | 0.4295 秒 |
| 直接构建总耗时 | 43.5121 秒 | 40.0282 秒 |

两次冷启动的主要差别来自依赖导入耗时，不能把总耗时差全部归因于代码优化。官方计算过程保持原样；删除重复数据库加载的收益有限。

优化后持久快照的首次读取为 0.5293 秒。随后 5 次序列化缓存命中为 0.4910、0.5864、0.5067、0.4695 和 0.4822 秒。每次都继续校验文件。独立剖析中，一次来源指纹计算耗时 0.292 秒，其中全部后端源码的读取与哈希占 0.174 秒；正常快照读取会检查两次来源指纹。因此，本次不声称服务器响应时间获得大幅下降。传输压缩和页面复用的效果应以各自验收结果为准。

## 输出一致性

在同一进程、同一份来源下，分别执行原来的两次数据库加载流程和新的单次加载流程，两次均独立调用官方完整性计算。完整响应逐字节相同，JSON 比较也相同，响应长度均为 1,266,559 字节。规范化 JSON 的 SHA-256 均为：

```text
dc4a6804687cfb5ae8b4bb26a2e842e4411f1494fe46a1466cb7b9dbf029f034
```

不同 Python 进程独立重算时曾出现不同响应哈希，本次没有据此宣称跨进程逐字节确定性。保持原计算与优化后计算在相同执行条件下的输出一致，是本次兼容性验证的范围。

## 部署准备

代码或来源更新后，目录可能需要重新计算。启动 API 后可先请求一次 `/api/v1/coverage`，等待成功后再交付访问。原有加载提示和 120 秒请求超时继续保留。预热成功后，后续服务重启可读取已验证的持久快照；来源指纹变化时仍重新构建。此次没有将科学初始化加入全站阻塞启动流程。
